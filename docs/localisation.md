# Safe Chain localisation

Flow: **UI string → `useT()` → language context → cached lookup (database) → provider chain → cache → display**.

## Languages and real provider support

| Language | Code | NLLB-200 | Vambo AI | JengaNLP | Lovable AI (fallback) |
|---|---|---|---|---|---|
| English (source) | `en` | — | — | — | — |
| Bemba | `bem` | yes (`bem_Latn`) | when configured | interface only | yes |
| Nyanja | `nya` | yes (`nya_Latn`) | when configured | interface only | yes |
| Tonga | `toi` | yes (`toi_Latn`) | not verified | interface only | yes |
| Lozi | `loz` | **not in NLLB-200** | not verified | interface only | yes |

No endpoint, model name or language code has been invented. Vambo and Jenga stay
disabled until their environment variables are set; Jenga's adapter throws a clear
"no API contract configured" error rather than guessing a payload.

## Environment variables (server-only, never `VITE_`)

- `NLLB_API_URL` (required to enable NLLB), `NLLB_API_KEY`, `NLLB_MODEL`
- `VAMBO_API_URL`, `VAMBO_API_KEY`
- `JENGA_API_URL`, `JENGA_API_KEY`
- `LOVABLE_API_KEY` (already provisioned) powers the Gemini fallback

## Caching

`public.translations` is the persistent cache, unique on `(translation_key, target_language)`.
`translation_key` is a deterministic hash of source text + context, so the same string is
never sent to a provider twice. Public page loads use `getTranslationsFn`, which reads the
cache only — it never calls an AI provider. Missing strings are generated by an admin
(`generateTranslationsFn`) or by the retranslate action in the dashboard.

## Fallback behaviour

Providers are tried in the order declared in `src/lib/i18n/config.ts`, skipping any that are
unconfigured or that do not support the language. If every provider fails, the English source
is displayed and the failure is recorded in `public.translation_failures` for administrators.
Users never see a translation error.

## Human review

Machine output is stored in both `machine_text` and `translated_text` with status
`machine_translated`. Only `approved` / `human_reviewed` / `machine_translated` rows are
readable publicly; a reviewer edits the text and sets `approved` in
`/admin/translations`. Ordinary users cannot modify translations — writes require the
`admin` or `super_admin` role, enforced both in RLS and in the server functions.

## Adding a language or provider

1. Add an entry to `LANGUAGES` in `src/lib/i18n/config.ts` with the codes the provider
   actually documents, and list its provider chain.
2. Add the code to `LANGUAGE_ORDER`.
3. For a new engine, create `src/lib/i18n/providers/<name>.server.ts` implementing
   `TranslationProvider`, register it in `providers/index.server.ts`, and add its
   `ProviderId` to the config union.

Nothing in the frontend changes: the selector, cache and review dashboard pick the new
language up automatically.
